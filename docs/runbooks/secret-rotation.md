# Secret Rotation

Rotate a credential at its authority and update its consumers in a planned order. Changing a Kubernetes Secret does not necessarily change an application's stored password or restart a process using an environment variable.

## Procedure

1. Identify the Vault field, target ExternalSecrets and all consumers from the [secret inventory](../architecture/secrets.md). Record whether the application reads it at startup, reloads it, or stores its own copy in a database.
2. Establish a tested recovery/admin session and create the replacement credential at its authority when appropriate. Database, API and OIDC secrets can require different ordering or a temporary overlap.
3. Export an authorized `VAULT_TOKEN`, read the value privately and patch one field:

    ```bash
    read -rs VAL
    export VAL
    make vault-put-secret SECRET_PATH=infrastructure/minio KEY=rootPassword
    unset VAL
    ```

    The helper preserves sibling keys and refuses an unsafe overwrite after a failed patch. A complete `vault kv put` deliberately replaces every field at a path and should not be used for an ordinary single-field rotation.

4. Wait for ESO or request an immediate refresh:

    ```bash
    kubectl annotate externalsecret -n <namespace> <name> \
      force-sync=$(date +%s) --overwrite
    kubectl get externalsecret -n <namespace> <name>
    ```

5. Reload/restart consumers through their documented mechanism. Reloader's cluster-wide watch does not mean automatic rollout for every workload: the workload must opt in through annotations. Verify those annotations or perform a deliberate rollout.
6. Test actual authentication and dependent application requests, then revoke the old credential if supported. A `SecretSynced` condition proves synchronization, not that every consumer accepts the new value.

## Bootstrap credentials

The `vault-aws-kms` Secret and credentials needed to recover the backup store must remain available outside Vault. Do not revoke the only working KMS/backup credential before confirming its replacement works. Root/recovery material generated by `make vault-init` is saved privately; keep it in the designated password manager and remove the local file after verifying the stored copy.

The [ExternalSecret manifests](../architecture/secrets.md#vault-path-structure) are the authoritative path/property inventory. Recyclarr, Exportarr and other shared media consumers read keys from `apps/arr`; they are not independent API-key authorities.
